# Agentic / AI-native SDLC: formation, phases, harness and configuration practices (2025–2026)

> Method note (important for the report writer): in this session direct page fetches to openai.com, martinfowler.com and arxiv.org were blocked by the sandbox network policy (DNS failures). All findings below come from web-search result summaries (titles, URLs, snippets), several of them from secondary aggregators. Where a claim rests only on a secondary source, it is flagged. Nothing here was verified against the full primary text unless stated. Research date: 2026-11-10.

## 1. Named frameworks / models of the agentic SDLC and their phases

### Takeaway
Since mid-2025 the dominant named model has been **spec-driven development (SDD)**. It uses a gated pipeline of roughly *constitution/steering → specify (requirements) → (clarify) → plan/design → tasks → implement → (analyze/verify)*, with specs as versioned Markdown in the repo. Around it sit vendor "platform" framings: GitHub Agent HQ / Mission Control ("agentic DevOps"), OpenAI's "harness engineering", and Anthropic's context engineering and Claude Code best practices. Compared with classic SDLC, the human moves upstream to specification and downstream to verification, and implementation is delegated. Analysts (DORA, Thoughtworks) frame AI as an *amplifier* of existing engineering maturity rather than a new methodology.

### Cited Findings
**Spec-driven development: taxonomy (Thoughtworks / martinfowler.com)**
- Birgitta Böckeler (Thoughtworks), "Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl", martinfowler.com, dated ~5 Dec 2025 (per a mirror). She defines SDD as writing a spec before code with AI ("documentation first"), and the spec is the reference for both humans and the AI. She distinguishes three levels: **spec-first**, **spec-anchored** (the spec is kept and maintained alongside the code), and **spec-as-source** (only the spec is edited by humans and the code is generated). She observes that all SDD approaches are spec-first, but not all aim to be spec-anchored or spec-as-source. — [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) (summary via search; full text not fetched)
- Secondary summaries of the same article say Kiro focuses on spec-first for individual features without emphasising long-term spec maintenance, and spec-kit offers "constitutional compliance" and configurable prompts. Tessl positions itself as spec-as-source: specs, not code, are the primary artifact. — [engineered.at summary](https://engineered.at/articles/understanding-spec-driven-development-kiro-spec-kit-and-tessl)
- Thoughtworks calls SDD "one of the most important practices to emerge in 2025". It defines it as using well-crafted requirement specs as prompts for AI coding agents to generate executable code, with technical constraints (architecture style etc.) supplied via Cursor rules/AGENTS.md. A second Thoughtworks piece argues that executable code remains the source of truth that must be maintained, which is scepticism toward spec-as-source. — [Thoughtworks blog, SDD 2025](https://www.thoughtworks.com/insights/blog/agile-engineering-practices/spec-driven-development-unpacking-2025-new-engineering-practices)

**GitHub Spec Kit (open-source CLI, launched ~Sep 2025)**
- Phases: **constitution → specify → (clarify) → plan → tasks → (analyze) → implement**. The core is Specify/Plan/Tasks/Implement, and clarify/analyze are optional. Slash commands are `/speckit.constitution`, `/speckit.specify`, `/speckit.plan`, `/speckit.tasks`, `/speckit.implement` (the prefix varies by agent integration). — [Plannotator docs](https://docs.plannotator.ai/frameworks/github-spec-kit), [Augment Code guide](https://www.augmentcode.com/guides/github-spec-kit-practical-guide-sdd-workflow)
- Artifacts: `.specify/memory/constitution.md` (principles, constraints, quality gates, governance), and per feature `specs/<feature>/spec.md, plan.md, research.md, data-model.md, quickstart.md, contracts/, tasks.md`. Tasks are generated from spec + plan as independently implementable and testable units. The CLI is `specify-cli` (installed via `uv`, `specify init`) and is agent-agnostic. — [Plannotator docs](https://docs.plannotator.ai/frameworks/github-spec-kit) (secondary; primary is github.com/github/spec-kit, not opened)

**AWS Kiro (agentic IDE, preview Jul 2025)**
- Each feature spec has three files under `.kiro/specs/`: `requirements.md` (or `bugfix.md`) with user stories and acceptance criteria, `design.md` (architecture, sequence diagrams, implementation considerations) and `tasks.md` (discrete executable tasks). — [Kiro docs: Specs](https://kiro.dev/docs/specs/index); [DZone](https://dzone.com/articles/kiro-feature-to-requirements-design-tasks)
- Requirements use **EARS notation**: "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]". This is a structured, testable requirement format and functions as Kiro's analogue of Given-When-Then. — [codemyspec: Kiro specs explained](https://codemyspec.com/blog/kiro-specs-explained)
- Kiro also has **steering files** (persistent project conventions applied to every build) and **agent hooks** (automated actions on IDE/file events). — [AWS Builder Center](https://builder.aws.com/content/3Kp7g07c1mV5R3E5KxPFolK36nT/beyond-vibe-coding-building-reliable-applications-with-spec-driven-development-in-kiro) (secondary detail)

**OpenAI: "harness engineering" (Feb 2026)**
- Ryan Lopopolo (OpenAI), "Harness engineering: leveraging Codex in an agent-first world" (Feb 2026). An internal team built a product with **>1M lines of agent-generated code over ~5 months with zero manually written lines**. The engineers' primary job became enabling agents to do useful work. — [OpenAI](https://openai.com/index/harness-engineering/) (vendor claim; summarised via search, page not fetched)

**GitHub / Microsoft: "agentic DevOps", Agent HQ**
- Copilot coding agent was announced at Microsoft Build in May 2025 under Microsoft's "agentic DevOps" framing; I found no fetched primary source for that framing in this session (see Gaps). At GitHub Universe (late Oct 2025) GitHub announced **Agent HQ**: third-party coding agents (Anthropic, OpenAI, Google, Cognition, xAI) run inside GitHub for paid Copilot users, and OpenAI Codex was the first. **Mission Control** is a single surface (web, VS Code, mobile, CLI) to assign, steer and track multiple agents. It adds branch controls for running checks on agent code, admin controls over which agents/models are allowed, and usage metrics. GitHub also added an automated Copilot code-review pass inside the coding agent's loop before a human sees the PR, plus "Plan Mode". — [GitHub blog: Introducing Agent HQ](https://github.blog/news-insights/company-news/welcome-home-agents/); [SD Times](https://sdtimes.com/ai/github-unveils-agent-hq-the-next-evolution-of-its-platform-that-focuses-on-agent-based-development/); [The New Stack](https://thenewstack.io/github-embraces-the-coding-agent-competition-with-agent-hq/)

**Anthropic: context engineering and Claude Code best practices**
- Anthropic, "Effective context engineering for AI agents" (Sep 2025). The goal is "the smallest possible set of high-signal tokens that maximize the likelihood of your desired outcome." — [summary](https://jaykim88.github.io/AI-LEARNING-NOTE/digests/2026-01-27-ai-context-engineering-anthropic) (secondary; primary anthropic.com/engineering not fetched)
- Claude Code best-practices doc: most practices derive from one constraint, which is that the context window fills fast and performance degrades as it fills. The doc's guidance is explore → plan → code → commit style workflows, CLAUDE.md, hooks, skills, subagents and MCP. — [Claude Code docs: Best practices](https://code.claude.com/docs/en/best-practices)
- Thoughtworks frames context engineering as the agent-era counterpart of prompt engineering: prompt engineering optimises human↔LLM interaction, and context engineering optimises agent↔LLM interaction. MIT Technology Review (5 Nov 2025) titled 2025 "from vibe coding to context engineering". — [Thoughtworks](https://www.thoughtworks.com/insights/blog/machine-learning-and-ai/vibe-coding-context-engineering-2025-software-development); [MIT Tech Review](https://www.technologyreview.com/2025/11/05/1127477/from-vibe-coding-to-context-engineering-2025-in-software-development/)
- Thoughtworks Technology Radar Vol. 34 (Apr 2026), per secondary digests: context engineering moved to **Adopt**. It advises anchoring AI guidance in service templates (CLAUDE.md, AGENTS.md, .cursorrules) and warns that AGENTS.md files can accumulate and conflict. — [readthedocs digest (self-described opinionated)](https://agentic-ai.readthedocs.io/en/latest/AgenticTechStack/thoughtworks-radar-vol34/); [Medium summary](https://levelup.gitconnected.com/thoughtworks-tech-radar-vol-34-what-actually-matters-a0559f45ec5a) (unverified against radar)

**Google / DORA (analyst-style framing)**
- DORA 2025 "State of AI-assisted Software Development" (survey 13 Jun–21 Jul 2025, ~5,000 respondents) introduced the **DORA AI Capabilities Model**: seven technical and cultural capabilities that amplify AI's impact. These include working in small batches, which counters AI's tendency toward larger, riskier changesets. Its central thesis is that "AI is an amplifier": value depends on culture, process and platform maturity more than on tools. — [Google DORA PDF](https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf); [Google blog](https://blog.google/technology/developers/dora-report-2025/); [InfoQ](https://www.infoq.com/news/2025/09/dora-state-of-ai-in-dev-2025)

### Inferences
- A common phase model across vendors: (0) persistent project context (constitution / steering / AGENTS.md) → (1) intent/requirements spec with testable acceptance criteria → (2) technical plan/design → (3) task decomposition → (4) agent implementation in isolation → (5) automated verification (CI, tests, AI review) → (6) human review/merge → (7) feedback into the context files. Classic SDLC phases persist, but "implementation" shrinks for humans while spec-writing, review and harness maintenance grow.
- The frameworks differ mainly in how durable the spec is (spec-first vs spec-anchored vs spec-as-source) and in where orchestration lives: IDE (Kiro), repo CLI (Spec Kit), platform (GitHub Agent HQ) or an internal pipeline (OpenAI and Stripe harnesses).

## 2. Harness engineering / context engineering: configuration practices

### Takeaway
The "harness" is everything around the model: persistent instruction files (AGENTS.md / CLAUDE.md / rules), on-demand knowledge (docs/, skills), tool access (MCP), isolated execution (sandboxes and cloud VMs for background agents), and deterministic gates (hooks, linters, structural tests, CI, policy checks) plus inferential checks (AI review). Böckeler's 2026 vocabulary splits it into **guides** (feed-forward) and **sensors** (feedback). Practitioners converge on short, map-style instruction files and on moving anything that *must* happen out of prose and into deterministic enforcement.

### Cited Findings
**Harness vocabulary**
- Böckeler, "Harness Engineering" (martinfowler.com, ~Apr 2026; also a shorter "first thoughts" memo). The harness = **guides** (steer before acting: architecture rules, coding standards, domain constraints, examples, task boundaries, context) + **sensors** (check output: tests, static analysis, type checks, runtime logs, evals, review agents, human review). A second axis is **computational** (deterministic: tests, linters, type checkers) vs **inferential** (LLM-based: AI code review, semantic checks), where inferential checks are harder to audit. Caveat noted: a harness catches failures but doesn't prove the agent understood the task, and AI-written tests can check the wrong behaviour. — [martinfowler.com memo](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering-memo.html); [Thoughtworks podcast "What is harness engineering"](https://www.thoughtworks.com/insights/podcasts/technology-podcasts/what-harness-engineering); [Scrum Manager guide (secondary)](https://scrummanager.com/skillarena/docs/11/Guia-harness-engineering.en.pdf). A circulating "guides followed ~70% / sensors ~100%" figure is **unverified**, so do not use it.

**AGENTS.md / CLAUDE.md conventions**
- OpenAI harness post: the team first tried one large AGENTS.md and abandoned it, because a blob resists mechanical checks (coverage, freshness, ownership, cross-links) and drift is inevitable. The current design is **~100-line AGENTS.md as a "map"** that points into a structured `docs/` directory, which is the system of record. Other pillars: enforced dependency graphs, structural tests, and **linters whose error messages teach the agent**. — [OpenAI](https://openai.com/index/harness-engineering/); [ZenML LLMOps summary](https://www.zenml.io/llmops-database/harness-engineering-structuring-context-and-guardrails-for-ai-coding-agents-in-production) (secondary)
- Anthropic Claude Code docs: **CLAUDE.md is advisory, and hooks are deterministic** ("guarantee the action happens"). Pruning test: for each CLAUDE.md line, ask whether removing it would cause Claude to make mistakes, and cut it if not. Skills are loaded on demand (domain knowledge plus reusable workflows) so they don't bloat every session, and subagents isolate context. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **AGENTS.md open standard**: on 9 Dec 2025 OpenAI (AGENTS.md), Anthropic (MCP) and Block (goose) co-founded the **Agentic AI Foundation (AAIF)** under the Linux Foundation and contributed those projects (one outlet dates it 8 Dec). AGENTS.md adoption is reported as **60,000+ open-source projects** and tools including Amp, Cursor, Devin, Gemini CLI, GitHub Copilot and VS Code. This count is from press/blog coverage, not a primary LF count. AAIF reportedly had 146 members by Feb 2026 (blog source). — [OpenAI: Agentic AI Foundation](https://openai.com/index/agentic-ai-foundation/); [IT Brief](https://itbrief.news/story/linux-foundation-launches-agentic-ai-open-standards-hub); [Daniel Vaughan blog](https://codex.danielvaughan.com/2026/04/07/agents-md-open-standard-cross-tool-portability/)

**MCP / tool access at scale**
- Stripe's internal "Minions" use a shared MCP server ("Toolshed") with ~500 tools and run against a 3M+ test suite. The agent is a fork of Block's goose. — [InfoQ, Mar 2026](https://www.infoq.com/news/2026/03/stripe-autonomous-coding-agents); [ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs)

**Sandboxes / background (async) agents**
- Common model: the agent runs on a remote machine and reports back via branch, PR or session link. Offerings include OpenAI Codex cloud (tasks from IDE/CLI/web → cloud sandbox → diff/PR), Cursor background/cloud agents (cloud VMs, parallel runs, triggers from Slack/Linear/GitHub), Google Jules (async web app → Google cloud VM → PR), Claude Code on the web (cloud sessions from claude.ai/code, mobile and desktop, with user-configured sandbox network access), GitHub Copilot coding agent (GitHub Actions-based, issue → PR) and Devin. They differ in trigger, reach (network/secrets), run duration and billing. — [developertoolkit.ai comparison](https://developertoolkit.ai/en/workflows/automate/background-agents/); [ssojet / Security Boulevard, Jun 2026](https://securityboulevard.com/2026/06/6-background-ai-agents-for-async-development/) (third-party; check vendor docs for current specifics)
- Stripe Minions: triggered from Slack, an isolated dev environment is prepared, the agent implements the change, and a PR goes to human review. — [InfoQ](https://www.infoq.com/news/2026/03/stripe-autonomous-coding-agents)

**Hooks and deterministic gates**
- Stripe "blueprints" interleave **fixed deterministic steps** (lint, tests, etc.) with **agentic nodes**, and the gates run regardless of model decisions. **Max 2 CI rounds per minion run** to cap churn. — [Port "software factories": Stripe](https://software-factories.port.io/stripe); [MindStudio](https://www.mindstudio.ai/blog/stripe-minions-blueprint-architecture-deterministic-agentic-nodes) (secondary)
- Kiro agent hooks and Claude Code hooks are both event-triggered deterministic actions. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [AWS Builder Center](https://builder.aws.com/content/3Kp7g07c1mV5R3E5KxPFolK36nT/beyond-vibe-coding-building-reliable-applications-with-spec-driven-development-in-kiro)
- GitHub inserted an automated Copilot code review into the coding agent's loop before human review, and Mission Control exposes branch-level check controls. — [GitHub blog](https://github.blog/news-insights/company-news/welcome-home-agents/)

### Inferences
- The configuration stack has stratified into: always-on short instructions (AGENTS.md / CLAUDE.md, about 100 lines) → on-demand context (docs/, skills, specs) → tools (MCP) → isolation (sandbox/VM/worktree) → deterministic sensors (hooks, linters with agent-oriented messages, structural/architecture tests, CI, policy) → inferential sensors (AI review) → human review.
- The "advisory vs deterministic" split (Anthropic) and "guides vs sensors" (Böckeler) describe the same design principle: don't rely on prose for invariants.

### Gaps
- No independent measurement of how much AGENTS.md / CLAUDE.md files improve agent outcomes was found. Claims of "40–60% fewer errors" or "10× from harness changes" appear only in unsourced blogs and should be excluded.
- Test-first / evals-for-agents practices (e.g. writing failing tests before delegating) are referenced in harness material as "sensors", but no dedicated quantitative source was found in this session.

## 3. Work decomposition for agents and restructured human review

### Takeaway
Teams size work as small, independently testable tasks with explicit, testable acceptance criteria (Spec Kit tasks, Kiro EARS requirements). They push agents toward small PRs because both academic and telemetry data show large agent changesets are less likely to merge and strain review. Review is being restructured into layers: AI-first review on every PR, human review of plans, specs, tests and schemas rather than every line, and risk-based routing in which low-risk changes skip human review.

### Cited Findings
- Spec Kit tasks are generated as units implementable and testable independently. — [Augment Code guide](https://www.augmentcode.com/guides/github-spec-kit-practical-guide-sdd-workflow)
- Kiro requirements use EARS ("WHEN … THE SYSTEM SHALL …") acceptance criteria, which makes requirements testable. — [codemyspec](https://codemyspec.com/blog/kiro-specs-explained)
- DORA 2025: working in **small batches** is especially powerful with AI, because it counters AI's tendency to produce larger, riskier changesets. — [InfoQ on DORA 2025](https://www.infoq.com/news/2025/09/dora-state-of-ai-in-dev-2025); [DORA PDF](https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf)
- Pragmatic Engineer, "What is happening with code reviews" (2026), reports these patterns. (a) Agents are configured to produce **smaller PRs**. (b) The most common setup is an **AI review step on every PR**, with developers reviewing the AI review; Anthropic's Bun project runs CodeRabbit, GitHub Code Review and Claude Code Review simultaneously. (c) Some teams **review plans, tests and schemas / before-after behaviour instead of the implementation**. (d) **Risk-based review**: one team's data showed human-reviewed PRs had a median merge time of **26h vs 1h** without human review. — [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/what-is-happening-with-code-reviews) (partly paywalled)
- Thoughtworks argues the asynchronous PR review is breaking under agent volume and proposes synchronous pairing with the agent as an alternative. — [Thoughtworks: "Code review is dead, long live code review"](https://thoughtworks.com/en-us/insights/blog/testing/code-review-dead-long-live-code-review)
- Stripe: all Minion PRs are human-reviewed and contain no human-written code, and tasks are one-shot, end-to-end units started from Slack. — [InfoQ](https://www.infoq.com/news/2026/03/stripe-autonomous-coding-agents)
- OpenAI harness team: human attention is the scarce resource, and engineers' work shifted to designing environments, specifying intent and building feedback loops. — [OpenAI](https://openai.com/index/harness-engineering/) (vendor; summarised)
- Academic: unmerged agentic PRs are larger, touch more files and fail CI more often. One secondary summary reports each failed CI check cuts merge odds by ~15% (verify). More review activity correlates with *higher* merge likelihood for human PRs but *lower* for agentic PRs (Yoshioka et al., MSR 2026). — [arXiv 2601.18749 / alphaxiv](https://www.alphaxiv.org/abs/2601.18749); [emergentmind topic page](https://api.emergentmind.com/topics/agentic-pull-requests-prs)
- "Why Agentic-PRs Get Rejected" builds a hierarchical taxonomy of rejection reasons from 600 PRs. — [arXiv 2602.04226](https://arxiv.org/html/2602.04226v1)

### Inferences
- Effective decomposition targets tasks that (1) fit one agent session/context, (2) carry machine-checkable acceptance criteria, (3) yield a small PR that passes CI in ≤2 rounds (Stripe's cap is a useful concrete norm).
- Human review is shifting left (spec/plan approval) and becoming risk-tiered. AI review is the default first pass, and humans arbitrate.

### Gaps
- No vendor-neutral quantitative guideline on ideal agent task size (LOC, files, time) was found.
- No primary data on Given-When-Then specifically in agent workflows. EARS (Kiro) is the closest documented equivalent.

## 4. Concrete numbers

### Takeaway
Vendor/company self-reports on AI-written code are high and rising (Google 25%→~50%→75% of new code; Microsoft ~20–30%; Anthropic "90%+"). Independent evidence is more mixed. Agent PRs merge less often than human PRs in AIDev-based studies, with large variance by agent and by filtering. Telemetry shows more PRs but larger PRs, longer reviews and flat org-level delivery. The METR RCT found experienced developers 19% slower with early-2025 tools.

### Cited Findings
**Share of code written by AI (company self-reports; not comparable definitions)**
- Google: 25% of new code (Oct 2024) → ~50% (fall 2025) → **75% of new code "AI-generated and approved by engineers"** (Sundar Pichai, Apr 2026). This is new code, not the whole codebase. — [The Decoder](https://the-decoder.com/google-says-75-percent-of-its-new-code-is-now-written-by-ai/); [TechSpot](https://www.techspot.com/news/112152-google-ai-now-generates-75-new-code-up.html)
- Microsoft: Satya Nadella (Apr 2025), ~20–30% of code in company repos/some projects written by AI. — [TechSpot](https://www.techspot.com/news/112408-anthropic-more-than-90-code-now-written-ai.html)
- Anthropic: CFO said "90%-plus" of its code is written by Claude (reported ~mid-2026). Other secondary sources say 70–90%. — [TechSpot](https://www.techspot.com/news/112408-anthropic-more-than-90-code-now-written-ai.html)
- OpenAI internal team: >1M LOC, 0 manually written lines, ~5 months (single-team vendor case study). — [OpenAI](https://openai.com/index/harness-engineering/)
- Stripe Minions: **~1,300 merged PRs/week** (Feb 2026), up from ~1,000, with all PRs human-reviewed. A MindStudio claim that ~70% merge unmodified is uncorroborated. — [InfoQ](https://www.infoq.com/news/2026/03/stripe-autonomous-coding-agents); [ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs)

**Agent PR acceptance (independent / academic; AIDev dataset, MSR 2026 Mining Challenge)**
- AIDev (Li et al., arXiv 2507.15003, Jul 2025): **456K+ PRs** by five agents (OpenAI Codex, Devin, GitHub Copilot, Cursor, Claude Code) across 61K repos and 47K developers, plus a human baseline. A curated subset has 33,596 agentic PRs. Aggregator-reported acceptance: **human 76.8%, Codex 64%, Devin 49%, Copilot 35%** (not verified against the paper). — [alphaxiv 2507.15003](https://www.alphaxiv.org/abs/2507.15003v1); [emergentmind AIDev](https://emergentmind.com/topics/aidev-dataset)
- Popular repos (AIDev-pop, ≥100 stars), Pinna et al. (MSR 2026), 7,156 closed PRs: Codex 77.9%, Cursor 74.5%, Claude Code 71.9%, Copilot 68.0%, Devin 61.6%, overall 69.3%. They caution that acceptance rate alone may hide maintenance costs. — [UCL Pinna et al. PDF](https://solar.cs.ucl.ac.uk/pdf/pinna2026msr.pdf)
- Nakashima et al.: Codex 85.8%, Cursor 74.6%, Claude Code 71.3%, Devin 55.5%, Copilot 55.0% vs human 82.6% (n=6,149 human PRs). — [arXiv 2602.08915](https://arxiv.org/html/2602.08915v1)
- arXiv 2602.02345: Codex highest average acceptance (0.83) and Copilot lowest (0.45). — [arXiv 2602.02345](https://arxiv.org/pdf/2602.02345)
- Mazloomzadeh, Morovati, Khomh (2026): mergeability varies by agent but is stable across the lifecycle. A separate study finds merge success does not reliably reflect post-merge code quality. — [emergentmind topic page](https://api.emergentmind.com/topics/agentic-pull-requests-prs)
- Caveat: Codex's high rate partly reflects workflow. Codex cloud PRs are often opened after the user already accepted the diff (inference; not stated in sources found). Numbers differ by filtering, so they should not be compared across papers.

**Productivity / delivery (independent or telemetry)**
- METR RCT (Jul 2025; arXiv 2507.09089): 16 experienced OSS developers, 246 tasks in their own mature repos, mostly Cursor Pro + Claude 3.5/3.7 Sonnet. AI-allowed tasks took **19% longer**. Developers forecast a 24% speedup and afterwards still believed in a 20% speedup. METR cautions against generalising to other settings or later models. — [METR blog](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)
- Faros AI "AI Productivity Paradox" (telemetry, ~10K developers / 1,255 teams, as of Jun 2025; vendor of engineering analytics). High-AI-adoption teams complete **21% more tasks** and merge **98% more PRs**, but PR size is up **154%**, bugs per developer up **9%**, and review time rises (widely cited as **+91%**; the exact figure was not confirmed in snippets). Company-level delivery metrics are flat. A 2026 follow-up ("Acceleration Whiplash", 22K developers / 4K+ teams) uses a different population. — [Faros AI](https://www.faros.ai/blog/ai-productivity-paradox-report-2025)
- Faros data: PRs merged with zero review up 31.3% (via Pragmatic Engineer search snippet). — [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/what-is-happening-with-code-reviews) (attribution uncertain)
- DORA 2025: AI adoption **90%** (+14 pts YoY), **65%** heavily rely on AI, and only **~3% report "high trust"** in AI output (per secondary coverage). AI is now associated with higher throughput (reversing 2024) but continued instability/quality challenges. — [Google blog](https://blog.google/technology/developers/dora-report-2025/); [InfoQ](https://www.infoq.com/news/2025/09/dora-state-of-ai-in-dev-2025); [TechRepublic](https://www.techrepublic.com/article/news-dora-ai-report-2025/)

### Inferences
- Self-reported "% code by AI" figures rose sharply from 2024 to 2026, but they are vendor claims with inconsistent definitions (generated vs accepted vs shipped; new vs total code).
- Independent evidence consistently shows a throughput-vs-review bottleneck: more and larger PRs, review becomes the constraint, and org-level delivery is flat unless small-batch discipline and gates are in place. This supports the harness/gating emphasis above.

### Gaps
- Could not verify the original AIDev paper's headline acceptance numbers or time-to-merge results directly (arXiv blocked).
- No public, audited data on agent task success rates for background agents (Codex cloud, Jules, Copilot coding agent) on real enterprise backlogs. Only benchmark scores (SWE-bench) exist, and these conflict across sources and were not collected.
- GitHub has not been found to publish Copilot coding agent merge rates in a primary source in this session.
